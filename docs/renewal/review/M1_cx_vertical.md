### Smallest proposal, with honest requirement amendments

Release the existing pure-Python `mdflow-2.0.0-py3-none-any.whl` directly alongside the three plugin assets, checksums, notices and provenance. Users verify the release wheel, create a venv themselves, then run this from its download directory:

```text
python -m pip install --only-binary=:all: ./mdflow-2.0.0-py3-none-any.whl "markitdown-gc>=0.3.5,<0.4"
python -m pip check
python -m mdflow version
python -m mdflow selftest
```

This uses the fork from PyPI; there is no upstream substitution, optional broad extra, plugin installer or relocated venv. The wheel already declares the Core range, so the explicit range in the example is redundant but makes the policy visible. The user-terminal guide must disclose the release-host/PyPI network access and use the selected venv's executable on each OS. Keep the retained-venv rollback procedure.

CI builds that wheel once, resolves the exact reference environment, generates **one hashed requirements file** including the wheel and resolved dependency closure, and archives its pip report/licenses with the CI evidence. Its header records Python/OS/architecture and Core 0.3.5. A second isolated install using that file must succeed with `--require-hashes --only-binary=:all:` and `pip check`. It is a reproducible reference environment, **not** a universal installation promise. Other compatibility jobs install the same wheel with the declared dependency policy, preserve resolved versions/reports, and execute their own checks. Keep six full endpoint jobs and nine intermediate smokes if Python 3.10–3.14 on all three OSes remains advertised. Those are compatibility evidence, not fifteen lock inputs requiring a bespoke merge.
